## 摘要结论

gongchepu.net 的“卡拉 OK”不是按时间戳播放预录音频，而是一套完整的浏览器端工尺谱解析、节奏启发式展开、腔格展开和 Web Audio 合成器。其业务逻辑全部位于公开加载的 [`d0aa98a3e71c.js`](https://gongchepu.net/static/CACHE/js/d0aa98a3e71c.js)；reader 647 与 reader 858 在本次调查时加载完全相同的业务包，说明它是站点级通用实现，不是《寻梦》特例。

它有很高的工程参考价值，但不能整体复制为本项目的 MusicXML 事实解析器：

- **高度吻合**：工尺相对音级、`/` 向前附着、括号旁注音有时值、`h/s/d/c` 的名称、`1..8` 的大类分组、时值先于 BPM、完全不读取录像时间戳。
- **提供新增线索**：`5..8` 还具有“虚位/切分”的播放运行语义，可与 `1..4` 成对归一；有拍区间内，以一个板眼数字为一个抽象时值单位，再对无标音作二分式和模板式分配。
- **明确冲突**：网站会把气口、同音换字、长音收尾等主动变成休止；默认 `上=D5` 且 BPM=42；自动展开腔格并识别未明记的固定旋律模板；这些都不能不加标记地成为五线谱事实。
- **不具备 MusicXML 所需保证**：没有拍号、小节闭合、字段级证据状态、稳定源码范围、推定标记或 MusicXML 输出；解析容错和若干疑似代码错误也不适合作为严格转换器的失败边界。

因此，现行 spec 的总体架构不应被替换。应把该实现整理为一个版本化的 `gongchepu-playback-2020` **试听 profile**，从中提取测试向量和可审阅规则；唯一的规范 MusicXML 仍须保持“推定可见、可回溯，未知不冒充事实”，试听 profile 不导出第二份 MusicXML。

  -> splitTracks

## 3. GCN 源语法与解析行为

### 3.1 页面级语法

隐藏的 `<div id="gcn">` 是该站的事实输入。parser 按行识别：

| 前缀/形式 | 解释 |
| --- | --- |
| `;` | 注释 |
| `#` | 标题 |
| `=` | 念白/动作 |
| `>` | 夹白 |
| `【曲牌】（调门）` | 曲牌与可选调门 |
| `\pz{...}` | 附着到前一个 cell 的批注 |
| `\sd{陰平...}` | 给唱词 cell 标字调 |
| `字{工尺串}` | 唱词和工尺 |
| `字-{...}` | 小字样式 |
| 第二、三组 `{...}` | 同一唱词的多行工尺 |

这比 `viewerModel.json` 丰富：后者是播放器/标注投影，缺少完整曲牌、调门、动作和原始行结构。两者共同支持现 spec 的核心决定——不能把扁平播放 JSON 当作唯一乐谱事实源；需要校订清单补回区段上下文。

### 3.2 工尺串 lexer

`parseNotesString` 的实际规则：

- 基字为 `合 四 一 上 尺 工 凡 六 五 乙`；
- 基字后允许任意个连续 `+` 或 `-`，代码可表达 `++/--`；
- 随后的连续数字整体存入 `beats`，不是重复发音；
- 半角或全角括号切换 `side=true/false`，状态可跨拆分 token 保持；
- `/` 不产生独立 token，而是向前找一个非零时 token 并设置 `qikou=true`；
- `h/s/d/c` 作为 note-like token 保留，名称分别为 `huoqiang/souqiang/dieqiang/cuoqiang`；
- 每个 display cell 只有 `{line, ch: 0}` 的粗源位置。

与现 spec 相比，唯一明确的词法扩展是重复音区符。spec 当前写“可选 `+` 或 `-`”，实现时应明确选择：接受重复符并表驱动验证合法音区，或把超出 profile 的组合报错；不能因当前 viewer 只见 `-1/0/1` 就静默截断。

网站 parser 非 fail-closed：未知非数字字符可能被保留为 token，未配对括号没有 fatal 诊断，非法音高到后续阶段才 `warn` 并可能跳过。现 spec 要求 source range 和结构错误停止，应该保留这一更严格边界。

## 4. 音高和定调

### 4.1 相对音高完全一致

网站的 `Note.NOTE_CHAR_MAP` 为：

| 工尺 | 相对半音 |
| --- | ---: |
| 合 | -5 |
| 四 | -3 |
| 一 | -1 |
| 上 | 0 |
| 尺 | 2 |
| 工 | 4 |
| 凡 | 5 |
| 六 | 7 |
| 五 | 9 |
| 乙 | 11 |

这与现 spec 的相对音级表相同。`+/-` 分别加减 12 半音；网站还支持两重符号至 ±24。

### 4.2 调门表大体相同，但不能照搬

播放器从当前轨道向前扫描曲牌的“（某字调）”或以“調”结尾的动作文字，查找：

| 名称 | 网站半音偏移（相对 C） |
| --- | ---: |
| 上字 | -2 |
| 尺字 | 0 |
| 小工/工字 | 2 |
| 凡字 | 4 |
| 六字 | 5 |
| 正宫/正工/五字 | 7 |
| 乙字 | 9 |

找不到时默认 `2`，即小工调/`1=D`。这与用户确认的默认音名一致。

但输出 MIDI 基准是 72（C5），所以网站默认实际合成 `上=D5`，比现 spec 的 `上=D4` 高一个八度；这是适合笛音合成的播放音区，不足以改写五线谱默认音区。另一个实质差异是网站凡字调取 E，而现研究依据正式地方标准采用约 E♭。因此只能复用调门名称识别，不能复用整张绝对调高表。

网站使用 `A4=440` 的十二平均律频率公式。它会在检测到某些北曲特征字时，让部分邻音模板改用七声音阶；这仍不等于拥有可审定的 `scaleProfile` 或传统律制。

## 5. `1..8` 板眼码：相容之处和新增运行语义

### 5.1 不应推翻现有类别表

关键常量是：

```text
有拍触发：1,2,3,4,6,7,8（单独的 5 不触发上板）
板类：    1,4,5,8
眼类：    3,7
其余类：  2,6
虚位类：  5,6,7,8
虚实配对：5->1, 6->2, 7->3, 8->4
```

这与现 spec 的语义分类其实相容：`1/4/5/8` 分别属于头板、赠板、底板、腰赠板；`3/7` 是中眼及其侧位；`2/6` 是小眼及其侧位。特别是数字 `5` 单独不建立有拍区段，并被 CSS 和变量上下文当作底板使用，支持现 spec “底板不是固定时长休止”的读法。

因此，`5->1 ... 8->4` 不能被误读为“网站认为 5 就是头板、8 就是赠板”。它发生在**播放预处理**：当有拍组从虚位数字开始时，代码把持续音拆成 continuation，先保留虚位，再将对应实位作为新的锚点，最后合并持续时值。这是现 spec 尚未写清的 `placement/切分` 运行语义，不是八个码的音乐学名称被推翻。

### 5.2 网站如何猜“散板/上板”

`splitByBanType` 默认从散板开始：

1. 遇到除 `5` 外的数字才进入有拍候选；
2. 观察板类和眼类交替后，才认为已经“上板”；
3. 上板后再遇连续板类，并且当前是实位 `1` 或 `4`，可切回散板；
4. 曲牌头会重置部分判定；
5. 连续无板眼唱词达到 5 个、无有效板眼唱词达到 8 个、小字唱词达到 3 个，强制切回散板；
6. 某些无数字 `s` 也会触发切分；
7. 句末可人工补一个虚拟 `5`，只有一个散板 token 的组还可能被并入下一组并补静音 `2`。

这些常数是为了“听起来可播放”而设的段落恢复启发式。现 spec 要求由校订 manifest/曲牌 profile 明确板式和 meter，不能将 5/8/3 个唱词阈值提升为昆曲通则。可以把网站结果作为候选诊断或人工校订建议。

### 5.3 网站没有拍号和小节

它不识别“一板一眼 2/4”“一板三眼 4/4”等拍格，也不建立 measure。板眼数字只把一条旋律分成抽象锚点组，并触发板声强弱：`1/4/5/8` strong，`3/7` weak，`2/6` weaker。

所以该代码不能证明现 spec 的默认拍号，也不能替代“小节时值闭合”验证。相反，它证明应把原始码、metric anchor、推定拍格分层保存。

## 6. 有拍时值算法

### 6.1 通用骨架

`parseShangban` 先把腔格变成实际 Note，再按“带板眼数字的音开始一个组”分组。默认每个组占 1 个抽象单位；若首音有多个连续板眼数字，则总长增加为数字个数。因此连续数字约束一个持续音跨越多个锚点，与现 spec 一致，不是重复音。

组内分配的默认算法是：

- 普通主音权重 1；
- 括号旁注音权重 0.5；
- 掇腔生成音（网站称 `cuoqiang`/撮腔）权重 0.5；
- 先按权重寻找接近一半的位置，递归二分总时值；
- 同一主音及其旁注音再按 `[1]`、`[3/4,1/4]`、`[1/2,1/4,1/4]` 分配；更多旁注使用主音双权重、其余等权的兜底。

这为现 spec 的“旁注音默认有时值”提供强实现旁证。但固定 0.5 权重只是该播放器的推定，不应被标为 `confirmed`。

### 6.2 有拍特殊模板

通用骨架之前，代码依次识别多组模板：

- 三音连续下行的花腔及其前缀；
- 5–7 音的大花腔；
- 四音上下往复；
- 两种固定“罕腔”音列；
- 擞腔处于组头、切分中段或跨锚点；
- 连续叠腔；
- 气口在组中不同位置；
- 豁腔位于组尾；
- 掇腔（网站称撮腔）、旁注音和切分组合。

常见比例包括 `2:1:1`、`1:1:2`、`3:1:2:2`、`3:1`、`1:1`，以及 1/2、1/4 的递归细分。它们产生的节奏通常适合播放，却没有规则 ID、曲牌限定或证据来源。后续审定只把通用分配骨架以及另有规范证据的叠腔、掇腔纳入 canonical score；本节其余特殊模板进入版本化 Playback Plan，并以紫色提示定位，不写成规范谱字段。

## 7. 散板算法

散板不是 `senza-misura` 下的最简排谱值，而是一套固定秒前时值模板。`parseSanban` 先以唱词 cell 为组，再按优先级匹配：

| 规则族 | 典型行为 |
| --- | --- |
| 单音/带腔 | `.9`；两音常为 `.4 + .5` |
| 豁腔 1–5 | 主音约 `.6/.7`，生成邻音约 `.3/.4`，并结合后音 |
| 入声/气口 | 主音 `.4`，插 `.2` 静止，再接后音 |
| 花腔/非花腔 | 三音常见 `.3+.4+.8` 或 `.5+.3+.3` |
| 擞腔 1–6 | 主音、上邻音和重复音的多段 `.2–.9` 模板 |
| 掇腔（网站称撮腔） | 主音 `.3`、同音 `.3`、后音 `.7` |
| 叠腔/三叠腔 | 重复前音；单叠约 `.3`，多叠使用 `.7/.5/.6` 等 |
| 旁注带腔 | 单个旁注常取 `.3` |
| 罕腔 | 固定相对音列取 `.3+.3+.6`，气口可再插 `.2` |
| 未匹配兜底 | 1 音 `.8`；2 音 `.4+.5`；3 音 `.5+.3+.3`；更多为若干 `.4` 加末音 `.5` |

后处理还会：

- 高音区 `+` 的音时值乘 1.3；
- 某些气口把前音拉至至少 `.9/1.2`，插 `.1/.3` 休止；
- 句末板位把音拉至至少 2.5，并插 `.4` 休止；
- 某些“慢散板”整组乘 1.5；
- 有拍转散板前对尾部逐渐乘 1 至 1.5。

这和现 spec 的 `senza-misura` 目标并不矛盾于“播放可以有速度”，但冲突于“这些数值是否是谱面事实”。建议：MusicXML 仍用最简、全部 `inferred` 的排谱时值；若需要复现网站听感，将上述值放入独立 playback realization，不回写 canonical duration。

## 8. 气口、旁注音和四种腔格

### 8.1 气口 `/`

parser 层与 spec 一致：`/` 附着前一发音事件，不独立造音。

player 层则明显不同：

- 有拍中创建 `NOTE_REST`，参与当前一拍的细分；
- 散板中常插 `.1/.2/.3` 休止并拉长相邻主音；
- 因位置不同选择不同节奏分支。

这是表现性 realization，而不是“气口等于固定休止”。现 spec 的默认 MusicXML 映射仍应只是 `breath-mark`；只有 profile 明确选择网站兼容听感时，才可另生成标为 `inferred` 的 rest。

### 8.2 括号旁注音

网站把旁注音设为 `half=true`，仍是有正时值的发音，通常权重为主音一半；并以小字 glyph 显示。它不是一律 grace note。这与现 spec 的默认决定相同，网站只是给出一个可选的 1:0.5 分配策略。

### 8.3 腔格展开

代码标识与本项目的兼容别名一致：`h=豁腔`、`s=擞腔`、`d=叠腔`、`c=cuoqiang/撮腔`；本项目按标准草案统一规范名为“掇腔”。网站的具体播放展开为：

- **豁腔 `h`**：从前音和可选后音推算一个较高邻音；对凡、乙有特例；生成音是半权重，合成器通常滑入。
- **擞腔 `s`**：围绕前音生成本音、上邻音和重复音序列；在不同切分位置会移动板眼标记或合并前组。
- **叠腔 `d`**：重复前一主音；多个 `d` 可形成多次重复。
- **掇腔 `c`（网站称撮腔）**：标记前音并增加同音的半权重音；有拍时常等分相关音。

网站还识别没有 `h/s/d/c` 明记的花腔、罕腔和入声模式。这些是最不应直接搬入 canonical score 的部分：模式可能与曲牌、南北曲、字调和传本有关，而代码只保存少量布尔上下文。它们可以成为“待谱师审定的候选 realization”，不能因一份播放器源码而变成 `confirmed`。

另有一个当前仓库实现问题：[`src/lib/gongche.js`](../../src/lib/gongche.js) 的 `ORN_LABEL` 仍写着 `h=橄榄/连、s=滑、d=断/顿、c=擞`，与已人工确认的 spec 及网站自身 `huo/sou/die/cuo` 命名都不一致。该显示标签应在后续实现任务中修正；本次研究不改产品代码。

### 8.4 掇腔：标准草案与网站的确定差异

标准草案把掇腔描述为有强弱层次的“顿—休—带”：前音实唱半拍，中间休止四分之一拍，后音轻带四分之一拍。网站则复制前音音高生成一个半权重音，不插入草案所述的中间休止；有拍时把相关音等分，散板时使用 `.3/.3/.7` 等播放常数。因而网站的同音复制是播放器近似，不是谱面确定的掇腔音高。

本项目的审定规则采用草案的结构与 `2:1:1` 比例，但明确不把草案所述的前置气口、平声字或出口位置当作有效性条件：只要 `raw` 中出现 `c` 就确认存在掇腔并尝试规范展开。中间休止的存在与比例为 `derived`，属于规范 MusicXML；其具体拍位和时值确定时为黑色，依赖推定时为橙色，绝不使用紫色。明记板眼优先于比例，不得移动锚点；不兼容但仍能容纳正时值休止时保留结构、将受影响时值标为 `inferred` 并报告 `DUOQIANG_ANCHOR_CONFLICT`；完全没有休止空间时保留原音和绿色标签，不生成零时值/grace rest，把展开标为 `unresolved` 并报告 `DUOQIANG_NO_METRIC_SPACE`。“带”保持正常大小、黑色且具有时值，不能写成 cue/grace note；绿色只标“掇腔”名称。查找“带”可跨 `gc` token 和唱词字，但不能越过确认的句界或曲牌边界；跨字“带”继续前字的 lyric extension，后一唱词只可在自身剩余工尺音中顺延。没有歌词落点时输出橙色待校文字和 `DUOQIANG_LYRIC_COLLISION`，不得连锁移动后续唱词。若边界内没有后续谱面音，则保留绿色腔格标签并报告 `DUOQIANG_MISSING_TRAILING_NOTE`，不得退回网站的同音复制。连续多个 `c` 只实现第一枚，其余报告 `DUPLICATE_DUOQIANG_CODE`。当前《寻梦》数据有 13 个包含 `c` 的 `raw`，全部只有一个 `c`，没有出现 `cc`；13 个“带”候选音都在同一唱词内，其中 12 个不带板眼，`line-68` 的“间”是唯一后音带板眼的 `尺2c → 上7`。网站算法仅可留在试听方案中，并以紫色编辑标记定位，不改变规范 MusicXML 的音符和休止。

## 9. 休止和发音后处理

网站生成的休止远多于输入显式信息：

- 气口休止；
- 相邻不同唱词 cell 恰为同音时，切出最多 `.05` 的微休止以重新发音；
- 有拍长音达到 4 单位、散板长音达到 3 单位时，尾部扣出 `.5` 休止；
- 散板句尾和板位模板中的 `.1–.4` 休止；
- 切分和孤立散板组可能生成 silent placeholder。

这些处理解释了网站为何“唱词清楚、句逗自然”，但它们不是原谱中显式休止。现 spec “只在确认的有拍结构出现未占 metric span 时推定休止；`/`、`5`、空 gc、视频间隙不单独造休止”的默认规则应保留。它们只能进入 Playback Plan，并在唯一的规范 MusicXML 上用紫色编辑提示定位；不得生成网站兼容的第二份 MusicXML，也不得改变其中的音符、休止或时值。

## 10. Web Audio、BPM 和手动模式

`GCNSynth` 的核心行为：

- 默认 BPM 42，可调范围 20–90，并支持两次敲击测速；
- `seconds = duration * 60 / bpm`；
- 用周期波 oscillator、滤波器和包络合成笛音；
- 相邻音程小于 7 半音时通常短滑音连接，较大跳进或重新发音直接切换；
- 时值大于 `.8` 的音启用约 5 Hz vibrato；
- 内嵌两段 MP3 作为强/弱板声；
- 用 `setTimeout` 串行调度，cell ID 命令负责页面高亮；
- 自动模式使用推定 duration；手动模式按回车推进下一发音，基本不依赖谱面时值。

因此该功能再次确认：播放时间可以由符号时值和可变 BPM 后置产生，无须读取每音录像时间戳。现 spec “时间戳不参与 MusicXML onset/duration/tempo”完全正确。

BPM 42 只是 UI 默认，不应自动写进 MusicXML metronome。网站振音、滑音和笛音包络也属于合成器表现层，不是谱面装饰事实。

## 12. 与现行 spec 的逐项对照

| 主题 | gongchepu.net | 当前 spec | 判断 |
| --- | --- | --- | --- |
| 权威输入 | 页面隐藏的原始 GCN 文本 | 经校订源中的 `gc.raw`，viewer 是投影 | 原则一致；本项目仍需 manifest 补足页面级上下文 |
| 时间戳 | 完全没有音符时间戳 | 禁止用 `s/e` 推时值 | 完全一致 |
| 相对音高 | 半音表与 `+/-` | 同一相对音级表 | 一致；补写重复 `++/--` 策略 |
| 默认定调 | 小工调，实际 `上=D5` | `1=D`，`上=D4` 且 inferred | pitch class 一致，音区不同；保留 spec |
| 凡字调 | E | 正式近似 profile 预计 E♭ | 冲突；不可照搬网站表 |
| 1..8 码义 | 板/眼/其余分组与虚位配对 | 八类语义类别 | 基本相容；spec 应增加虚实 placement 层 |
| 散/上板识别 | 依数字和 5/8/3 个唱词阈值猜测 | 依校订区段/profile | 网站只作候选诊断，不作事实 |
| 拍号/小节 | 不存在 | 明确 meter、measure closure | 网站无法替代 spec |
| 有拍细分 | 二分权重 + 大量模板 | 通用分配唯一命中时 `derived`，否则最简量化 `inferred` | 吸收通用骨架为 `kunqu-gcn-rhythm-v1`；特殊模板留在试听层 |
| 散板 | 固定小数时值并以 BPM 播放 | `senza-misura`，最简排谱值 | 分离 score duration 与 playback realization |
| 气口 | parser 附着；player 造休止 | `breath-mark`，默认不造 rest | 明确冲突；保留 spec 默认 |
| 旁注音 | 有时值，半权重 | 默认有时值、小尺寸；通用规则使用半权重 | 规则前提确定时可 `derived`，否则随上下文 `inferred` |
| h/s/d/c 名称 | 豁/擞/叠/`cuoqiang` | 豁/擞/叠/掇；撮、`cuoqiang` 为别名 | 语义一致，规范术语统一为掇腔 |
| 腔格 | 自动生成微观音列/时值 | `d/c` 有审定规范展开；`h/s` 暂保真名称 | 网站 `d` 提供旁证；网站 `c` 同音复制仅作试听；`h/s` 微观展开待审定 |
| 无标记模板 | 自动认花腔、罕腔、入声 | 不凭形似制造音 | 冲突；只可在审定 profile 中启用 |
| 休止 | 大量表现性自动休止 | 掇腔产生规范休止；其余只从 metric gap 推定 | 除掇腔外仍明确冲突，网站休止只进 Playback Plan |
| BPM | 默认 42 | 无证据不导 metronome | 明确冲突；42 只属播放 UI |
| 错误处理 | warn、跳过或返回空数组 | 结构错误 fatal，音乐不足局部 unresolved | spec 更适合可审计转换 |

| 通用性 | 同 bundle 服务多曲谱 | profile 通用且曲目可覆盖 | 架构方向一致；禁止硬编码《寻梦》 |

## 13. 可疑实现和风险边界

静态代码中至少有三处值得在兼容重写时设反例测试：

1. `calcShangbanDurations` 的一个分支使用 `a[i + 1] | []`，随后又把结果当数组遍历；这看起来本应是 `|| []`，当前分支很可能恒失效。
2. 同一函数的内部 helper 在 `e.length === 0` 时访问 `e[0].duration`，若异常输入抵达会崩溃；正常谱面可能使该路径不可达，但严格 parser 不能依赖这种偶然条件。
3. `playTrackFromCell` 开头调用全局 `stop()` 而非 `this.stop()`；浏览器中可能落到 `window.stop()`。UI 通常先主动停当前播放器，因而缺陷可能被遮蔽。

另有系统性风险：对象在虚位拆分、continuation 合并、腔格生成和后处理时被复制或突变，部分生成音没有 cell ID；所有时值都是 JS 浮点小数。若直接导出 MusicXML，会造成来源链断裂、不可见推定以及 `.30000000000000004` 一类值。重写时必须使用不可变 IR、稳定派生 ID 和有理数时值。

## 14. 审计后已纳入执行文档的决定

后续审定已把本报告的建议整合为以下执行规则：

1. **保留现有 1..8 名称表**，另存虚实/侧位 placement，不能压成单一拍数。
2. **无损接受重复音区符**，由 profile 判断可演奏性。
3. **建立 `gongchepu-playback-2020-v1`**，固定 asset URL、SHA-256、规则 ID、优先级和来源事件。
4. **只保留一个规范谱解释和一份 MusicXML**；试听效果进入独立 Playback Plan，不产生第二份谱。
5. **采纳网站通用有拍骨架为 `kunqu-gcn-rhythm-v1`**：板式确认、循环合法且规则唯一命中时为 `derived`，否则回退 `inferred` 最简量化；花腔、罕腔、入声等特殊模板不在此规则内。
6. **试听时值独立于规范时值**：BPM 和秒数只作用于 Playback Plan；紫色效果提示可定位到唯一 MusicXML，但不改变音符、休止和时值。
7. **不继承网站绝对音区和凡字调值**：保持 `上=D4 inferred` 与正式笛色 profile，并允许整体移调。
8. **`d` 进入规范谱同音重复；`c` 统一为掇腔**，采用经审定“顿—休—带”，网站同音复制只留试听；`h/s` 微观展开仍待审定。
9. **谱面颜色固定**：规范推定橙色、明记腔格绿色、试听效果紫色，紫色文字不加“试听”二字；MusicXML 不显示工尺字。
10. **每条网站规则建立最小 fixture，并保留全页回归**；全页统计只检测兼容实现漂移，不作为音乐学验收。

## 15. 最终判断

gongchepu.net 让当前 `viewerModel.gc.raw` 的格式获得了一个非常有价值的“可运行解释”，但没有让格式达到“完全解谜”：

- **语法、相对音高、码名和主要板眼类别**已经有强证据；
- **通用有拍分配、叠腔和掇腔**已有审定的规范处理，其他网站模板仍只是可复现试听规则；
- **准确五线谱所需的拍号、小节、曲牌级规则、传统调律、表演音区和证据状态**仍未由该代码解决；
- 网站的生成性启发式除逐条审定者外，不能倒灌成工尺原文或规范谱事实。

最终工程路线是：保留 Relative Score IR 与审计链，生成唯一 Canonical Score 和唯一 MusicXML；把已审定通用规则写成确定性规范转换，把其余网站规则重写为版本化、可开关、可测试的 Playback Plan。这样既能得到尽量准确的五线谱，又能提供网站兼容试听，并让每个推定或试听效果回到原始工尺位置和具体规则。
